## 1. 一句话讲清它是什么

一个跑在 **Cloudflare Workers + D1** 上的 Bitwarden 协议兼容服务端，
配一个**我们自己在源码里改过的** Bitwarden Web Vault 前端，
专门针对**手机浏览器**做了 19 批适配（底栏导航、输入框高度、下拉躲软键盘、深色主题等）。

客户端支持：官方 Bitwarden 手机 App / 浏览器扩展 / Web Vault 都能连。

## 2. 架构与分层（L1 / L2 / L3，L4 已退役）

```
┌──────────────────────────────────────────────────────────────┐
│ L3  前端（Web Vault）                                          │
│     Bitwarden 官方 Angular 应用，GPL-3.0                       │
│     源码在 fork：shiranzby/vw_web_builds @ shypwd              │
│     定制**直接写在源码里**（不是运行时打补丁）                    │
│     构建产物：bw_web_vault-<version>.tar.gz（≈36 MB）           │
└───────────────────────────┬──────────────────────────────────┘
                            │ 打进 public/web-vault/ 作为静态资源
┌───────────────────────────▼──────────────────────────────────┐
│ L1  后端（Cloudflare Worker）                                  │
│     Rust → WASM（worker-build），入口 src/entry.js             │
│     实现 /api/* /identity/* /notifications/*                   │
│     许可证：MIT（上游 warden，© 2025 Deep Gaurav）              │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│ L2  数据层（全部 Cloudflare 托管）                              │
│     D1 (SQLite)   —— 用户/条目/文件夹/组织/二步验证/Send         │
│     KV            —— 附件（可选，改 R2 见 wrangler.toml）        │
│     Durable Objects —— 推送通知 / CPU 卸载                      │
│     Rate Limiters —— 登录与 Send 访问限流                       │
└──────────────────────────────────────────────────────────────┘

L4（已退役）：曾是运行时注入的 `custom/custom.js` + `custom.css`。
  2026-09 起定制全部下沉到源码，L4 删除；线上两个路径固定 404，
  这个 404 本身就是"注入层确已退役"的判据。
```

**为什么 L3 的定制要改源码而不是运行时打补丁**：
运行时补丁依赖"上游产物的 DOM 结构不变"，上游一改就静默失效，且无法被构建期断言保护。
改源码后，每一批定制都能在 **CI 里对产物 grep** 出对应字面量（现在 27 组），
rebase 丢改动会立刻红，这是这条路上最大的收益。代价是要跟着上游 rebase（见 §7）。

## 4. 部署链路（先 build，后 deploy）

### 4.1 两条 workflow

| workflow（GitHub 里的显示名） | 文件 | 触发 | 干什么 |
|---|---|---|---|
| **`Build Web Vault (patched)`** | `build-web-vault.yaml` | **仅手动**（`workflow_dispatch`） | 拉 fork 源码 → `npm ci` → `dist:oss:selfhost` → 打 `bw_web_vault-<version>.tar.gz` → **27 组产物断言** → 传 artifact（保留 90 天） |
| **`Build`** | `push-cloudflare.yaml` | push `main` 自动 + 手动 | **按 artifact 名反查**最新未过期的构建 → 解压到 `public/web-vault` → 校验 → 替换 D1 ID → 建/迁 D1 → 导等价域名 → 写 secrets → `wrangler deploy` |

> ⚠️ **顺序不能反**：部署侧是"按 `bw_web_vault-<version>` 这个 artifact 名去反查"，
> 先 build 才有东西可查。
> ⚠️ **改 workflow 的那次 push 必须带 `[skip ci]`**：否则 push 触发自动部署，
> 而新版本号的 artifact 还不存在 → 部署必挂。

### 4.2 版本号"四处钉死"（最容易踩）

改版本必须同时改这四处，少一处 CI 就会红或部署错位：

| # | 位置 | 当前值 |
|---|---|---|
| 1 | fork `apps/web/package.json` 的 `version` | `2026.8.9` |
| 2 | fork `package-lock.json` 的 `packages["apps/web"].version` | `2026.8.9` |
| 3 | `build-web-vault.yaml` 的 `inputs.version` 默认值 | `v2026.8.9` |
| 4 | `push-cloudflare.yaml` 的 `BW_WEB_VERSION` 默认值 | `v2026.8.9` |

每批升 **patch 位**（`8.8 → 8.9`），让 `/vw-version.json` 自己成为"是否上线成功"的判据。
`apps/web/build/version.json` 是构建产物，**别手改**。

### 4.3 一次标准上线（命令照抄即可）

```bash
# ① fork：改源码 → commit → push 到 shypwd 分支
# ② 本仓库：改版本四处 / CI 断言 / 文档 → commit → push main（带 [skip ci]）

# ③ 触发构建（只发一次！别加 --retry-all-errors，会重复触发）
PAT=<你的 GitHub PAT>
curl -s --retry 3 -w "HTTP=%{http_code}\n" -X POST \
  -H "Authorization: Bearer $PAT" -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/<owner>/warden-worker/actions/workflows/build-web-vault.yaml/dispatches \
  -d '{"ref":"main","inputs":{"version":"v2026.8.9"}}'   # → 204

# ④ 等 build 绿 → 触发部署
curl -s --retry 3 -w "HTTP=%{http_code}\n" -X POST \
  -H "Authorization: Bearer $PAT" -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/<owner>/warden-worker/actions/workflows/push-cloudflare.yaml/dispatches \
  -d '{"ref":"main"}'                                     # → 204

# ⑤ 验证
curl -s https://<你的域名>/vw-version.json    # 期望 {"version":"2026.8.9"}
curl -s -o /dev/null -w "%{http_code}\n" https://<你的域名>/custom.js   # 期望 404
```

## 5. 一键部署到 Cloudflare（把这套给别人的最短路径）

> 好消息：**别人不需要 fork 那个 1.2 GB 的前端仓库**。
> `build-web-vault.yaml` 里的 `VAULT_REPO` 指向我们公开的 `shiranzby/vw_web_builds`，
> 谁 fork 本仓库都能直接构建出同样的定制前端。

### 5.1 准备（一次性）

1. Cloudflare 账号，记下 **Account ID**。
2. 建 D1 数据库（名字随意，建议 `vault1`），记下 **Database ID**。
3. 建 KV 命名空间（附件用，建议 `warden-attachments`），记下 **Namespace ID**。
   （想用 R2 存附件：改 `wrangler.toml` 注释掉的 `r2_buckets` 段，并设 secret `R2_NAME`。）
4. 建 API Token（**Global API Key 或带 Workers/D1 编辑权限的 token**）。
   ⚠️ 本项目的 workflow 用的是 `CLOUDFLARE_EMAIL` + `CLOUDFLARE_API_KEY`（Global Key），
   不是 Bearer token 方式。
5. 把 ID 填进 `wrangler.toml`（`database_id` / `kv_namespaces.id`），
   **或者**留 `${D1_DATABASE_ID}` 占位、走 secret（CI 会 sed 替换）。

### 5.2 三步进站

1. **Fork 本仓库**，在仓库 Settings → Secrets 里加：

   | Secret | 必填 | 说明 |
   |---|---|---|
   | `CLOUDFLARE_EMAIL` | ✅ | Cloudflare 登录邮箱 |
   | `CLOUDFLARE_API_KEY` | ✅ | Global API Key |
   | `CLOUDFLARE_ACCOUNT_ID` | ✅ | Account ID |
   | `D1_DATABASE_ID` | ✅ | D1 Database ID |
   | `ALLOWED_EMAILS` | ✅ | 允许注册的邮箱（逗号分隔；留空=不限制） |
   | `JWT_SECRET` | ✅ | 访问令牌密钥（随机长串） |
   | `JWT_REFRESH_SECRET` | ✅ | 刷新令牌密钥（随机长串） |
   | `R2_NAME` | ➖ | 用 R2 存附件时才需要 |

2. **跑一次构建**：Actions → `Build Web Vault (patched)` → Run workflow → `version` 填 `v2026.8.9`。
   （约 5 分钟；会跑 27 组断言，红了说明定制没进产物，别往下走。）
3. **跑一次部署**：Actions → `Build` → Run workflow。
   （会自动建表、导迁移、写运行时 secrets、发布。）

### 5.3 绑自己的域名

Cloudflare 控制台：
- **DNS**：加一条 `A` 记录指向 `192.0.2.1`（假源站，实际由 Worker 接管），开 Proxy（橙色云）。
- **Workers Routes**：`<你的域名>/*` → Worker `warden-worker`。

### 5.4 本地/命令行部署（不想用 Actions）

```bash
npm i -g wrangler
wrangler login
# 前端产物：从本仓库 Actions 的 bw_web_vault-v2026.8.9 artifact 下载后解压
tar -xzf bw_web_vault.tar.gz && mv web-vault public/web-vault
wrangler d1 migrations apply vault1 --remote
wrangler deploy
```

### 5.5 部署后自检清单

- [ ] `https://<域名>/vw-version.json` 返回期望版本
- [ ] `https://<域名>/custom.js` 与 `/custom.css` 都是 **404**（证明注入层没复活）
- [ ] 能注册/登录，能新建条目
- [ ] **手机浏览器**打开：底部有导航栏、输入框高度一致、深色主题能切
- [ ] 可选：跑一次线上验收脚本（§8）

## 6. 迁移工作指南（换账号 / 换环境）

### 6.1 数据迁移

| 数据 | 位置 | 迁移方式 |
|---|---|---|
| 主数据（用户/条目/ Send/组织/2FA） | D1 `vault1` | `wrangler d1 export vault1 --remote --output backup.sql` → 新环境 `wrangler d1 execute vault1 --remote --file backup.sql`。或用 `backup-d1.yaml` 的定时备份 |
| 附件 | KV / R2 | KV：`wrangler kv:bulk get` → `bulk put`；R2 用 `rclone` 或 `wrangler r2 object` |
| 表结构 | `migrations/` | 新库部署时自动 apply；空库还有 bootstrap 兜底 |
| 全局等价域名 | `sql/global_domains_seed.sql` | 部署流程会自动导（可用 `SEED_GLOBAL_DOMAINS=false` 关掉） |

> ⚠️ **用户的主密钥加密**：条目是用主密码派生的密钥加密的，
> 服务端**看不到明文**。迁移数据库不会导致数据不可读——只要用户自己记得主密码。
> 但**换了域名不影响解密**（加密与域名无关）。

### 6.2 配置迁移

按 §5.2 的 secrets 表逐个搬；另外 `wrangler.toml` 的 `[vars]` 里有
`DISABLE_USER_REGISTRATION`、`BASE_URL`、`PUSH_*` 等，按需同步。

### 6.3 前端迁移

前端产物**不在 git 里**，所以新环境必须重新构建一次（§5.2 第 2 步），
或者从旧环境拷贝 `public/web-vault/` 整个目录。

## 7. 上游跟进与长期维护

有**两条**上游线，节奏完全独立：

### 7.1 后端：`qaz741wsd856/warden-worker`（本仓库的 `origin`）

上游是 Rust 后端，改动频率低。跟进方式就是普通 fork 同步：

```bash
git fetch origin main
git log --oneline HEAD..origin/main      # 看看上游新增了什么
git merge origin/main                    # 或 rebase
# 重点看：migrations/ 有没有新增（有就让 CI 自动 apply）、wrangler.toml 有没有新增绑定
```

⚠️ 上游新增了绑定（新的 KV / DO / R2）时，`wrangler.toml` 里的 id 占位要同步补，
否则部署会红。

### 7.2 前端：`bitwarden/clients`（通过 `vaultwarden/vw_web_builds` 看官方 tag）

这是**主要工作量**。上游 Bitwarden 每月发版，前端要大版本跟进时：

1. **确认目标版本**：看 `bitwarden/clients` 的新 tag（如 `v2026.10.0`）。
2. **在 fork 里 rebase**：
   ```bash
   cd vw_web_builds
   git fetch upstream            # upstream = bitwarden/clients（或 vaultwarden/vw_web_builds）
   git rebase --onto v2026.10.0 v2026.8.0 shypwd
   ```
3. **冲突热点**（几乎每次都会撞）：
   - `apps/web/src/css/vaultwarden.css` —— 我们改得最多，且上游也动它
   - `libs/components/src/select/`、`disclosure/`、`toggle-group/`
   - `libs/tools/send/**`（Send 页我们重做过）
   - `apps/web/src/locales/{en,zh_CN}/messages.json`（我们加过 i18n key）
4. **改版本四处**（§4.2），跑一次构建。
5. **看 CI 那 27 组断言**：哪一组红了，就是哪一批的定制在 rebase 中丢了/被改坏了 ——
   这是当初坚持"每批都要有产物级字面量断言"的回报。
6. **跑运行期探针**（§8）。静态 grep 只能证明"字面量还在"，证明不了"行为对了"。

### 7.3 断言层为什么是你的安全网

`build-web-vault.yaml` 的第 11 步会对**真实产物**做 27 组断言：
每组既有**正向**（本批的字面量必须在产物里），也有**负向守卫**
（本批"只在窄屏生效"的规则不能被写成全局，否则桌面端跟着遭殃）。

负向守卫本身也要**离线证伪**一次（故意把规则提成顶格，确认它真的会报错），
否则它可能是一颗哑弹。脚本：`.deploycheck/probe-s15-guard.py`（已改成从 workflow 解析，不会漂移）。

### 7.4 建议节奏

| 频率 | 动作 |
|---|---|
| 每次改前端 | 改 → 本地构建 → `run-artifact-asserts.py` → 窄屏探针 → 上线 |
| 每月 | 看一眼上游 tag；不紧急就不跟 |
| 跟进大版本 | 预留半天：rebase + 冲突 + 27 组断言排错 + 探针 |
| 每季度 | 跑一次 D1 备份演练（备份没演练过等于没备份） |

## 8. 验证与回归工具箱（`.deploycheck/`）

> 该目录**默认整体 gitignore**，只有逐个加白名单的脚本才入库
> （目录里还有带测试账号明文的文件，**绝不能按扩展名批量放行**）。

| 脚本 | 作用 | 什么时候跑 |
|---|---|---|
| `run-artifact-asserts.py <build目录> [版本]` | 把 workflow 的 27 组断言脚本抽出来，在**你刚构建的产物**上实跑 | 每次改完前端、上线前 |
| `probe-s15-guard.py` | 负向守卫的**离线证伪**（故意改坏，确认守卫会报错） | 新增/修改了某批守卫后 |
| `probe-w19-verify.mjs` | 窄屏验收（当前批）。不带 `WARDEN_TEST_PROXY` 走本地 8099；带上走线上 | 每次上线前后 |
| `probe-v18-verify.mjs` / `probe-v18-live.mjs` | 第十八批（V 段）验收 | 回归 |
| `probe-b16-*.mjs`、`verify-batch*.mjs`、`falsify-b16.py` | 更早批次的探针 | 需要时 |
| `devserver-b8.config.js` | 本地 8099 dev server 配置（**给 proxy 挂了代理**，否则 API 全 504） | 起本地环境 |
| `b8-lib.mjs` | 公共库：登录、路由、TOTP、截图 | 被上面引用 |

用法示例：

```bash
# ① 产物断言（必须在构建之后跑，且 dev server 要先停，否则 build/ 会被 dev 产物顶掉）
python .deploycheck/run-artifact-asserts.py ../vw_web_builds/apps/web/build 2026.8.9

# ② 守卫证伪
```

## 9. 回滚与应急

| 场景 | 处置 |
|---|---|
| 新版本上线后有严重问题 | 把 `push-cloudflare.yaml` 的 `BW_WEB_VERSION` 改回上一个版本（如 `v2026.8.8`），push（**带 `[skip ci]`**），手动跑一次 `Build` 重新部署。**前端 artifact 保留 90 天**，旧版本可直接反查到 |
| 只是某一批定制有问题 | `git revert` fork 里那一批的提交 + 本仓库对应的 CI 断言组，再升版本号重新上线 |
| 误触发了多次构建 | GitHub Actions 里 cancel 多余的 run；**别用 `--retry-all-errors`**，那会把非幂等的 dispatch 重复发送 |
| 部署卡住 | 看 run 的**步骤级日志**（`poll-progress.sh` 可打"第 n/总步数 + 步骤名 + 时长 + 已失败步骤"）；关键关卡是 build 的第 11 步（断言）和 deploy 的 wrangler 发布 |
| 数据库误操作 | `docs/db-backup-recovery.md`；D1 有定时备份（`backup-d1.yaml`） |

## 11. 已知限制与后续建议

## 附录 B：常见故障速查

| 现象 | 原因 |
|---|---|
| 部署成功但页面是旧版 | 浏览器/Service Worker 缓存；或忘了先 build |
| `/custom.js` 返回 200 | 注入层复活了（不该发生），检查 `public/` |
| Actions 里 `❌ 版本不一致` | 源码 `package.json` 版本与 `inputs.version` 不符（§4.2） |
| 部署报"找不到 artifact" | 还没 build，或 artifact 名/版本对不上，或超 90 天过期 |
| 本地 dev server 登录后没反应 | webpack proxy 不读系统代理 → 必须用 `devserver-b8.config.js` |
| 断言全红但源码看着没问题 | 一定是"喂错文件"：断言脚本从 tar 里取文件，必须按 CI 布局打包（顶层 `web-vault/` + `vw-version.json`） |
