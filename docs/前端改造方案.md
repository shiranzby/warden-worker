# 前端改造方案评估（Apple 设计系统 / 是否自研前端）

> 起因：有人用 Open Design 做了一套 **Apple 风格**的 Web 前端（30 页 + 桌面壳 + 44 KB 设计系统 CSS），
> 问三件事：① 能不能改成这种样式？② 能不能在**源码层**改？③ 干脆**自己做一份前端**、不再跟上游？
>
> 结论先说：**① 能；② 能，而且现在就是源码层；③ 技术上可行但不建议从零写 —— 成本不在 UI，在加密。**
> 下面把"能到什么程度"和"哪一步开始"讲清楚。

---

## 0. 先盘清楚对方给的是什么

| 资产 | 内容 | 质量判断 |
|---|---|---|
| `pages/_shared/app.css` | 671 行 / 44.8 KB，**完整设计系统**：~120 个组件类 + 三套 scheme（`light` / `compact` / `dark`） | 结构干净，token 分层清楚（颜色/字阶/间距/圆角/阴影/动效/容器），可直接作为设计规范使用 |
| `pages/*.html` | 30 个静态页面，**从可运行原型真实渲染出来的**，共享同一份 `app.css` | 覆盖了当前功能的全部主要页面 |
| `shypwd-desktop-app.html` | 158 KB 单文件可运行原型（哈希路由，点侧栏走完全部页面） | 可交互，方便逐页评审 |
| `shypwd-pages.md` | 全页面审查索引 + **4 处按我们源码对齐的修正** | 说明对方**读过我们的 `vaultwarden.css`**（TOTP 徽章几何/动效、表格列、图标底色、聚焦环） |

## 1. ①③ 能改成这种样式吗？—— 分两层看，答案完全不同

### 1.1 视觉层（配色 / 字体 / 圆角 / 阴影 / 组件外观）：**能，而且不用改模板**

关键事实：本应用的样式底座有 **282 个 `--color-*` 变量**（`libs/components/src/tw-theme.css`），
深浅两套都在这里切换。**把这些变量重新赋值，整站配色就跟着变，一行模板都不用动。**

**已做实测**（`.deploycheck/.scratch-spike-apple-theme.mjs`，注入到线上真实应用）：

| 项 | 注入前 | 注入后 |
|---|---|---|
| `body` 字体 | `Inter, Helvetica Neue, …` | `"SF Pro Text", -apple-system, …` ✅ |
| `--color-primary-600`（主色） | `18 82 163` | **`0 113 227`**（Apple `#0071e3`）✅ |
| 正文文字色 | `rgb(27,32,41)` | **`rgb(29,29,31)`**（`#1d1d1f`）✅ |
| 深色主色 | `101 171 255` | **`41 151 255`**（`#2997ff`）✅ |
| 注入成功率 | — | **5/5 条规则**（`adoptedStyleSheets`，绕过 CSP） |

截图：`spike-apple/00-before-vault.png` → `01-after-vault-light.png` → `02-after-vault-dark.png`
→ `03-after-settings.png` → `04-after-dialog.png`。

> 这次是**运行时注入**，只为快速验证"映射关系成立"。真正落地要写成
> `apps/web/src/css/vaultwarden.css` 里的**覆盖层**（下一个"段"），走现有 29 组断言流程。

**视觉层能拿到的**：配色、字阶、圆角、阴影、聚焦环、按钮/输入框/卡片外观、密度（紧凑式）、深色。
**视觉层拿不到的**：布局结构（见下）。

### 1.2 信息架构层（左侧图标栏 + 中间列表 + 右侧详情的三栏）：
### **不能只换 CSS** —— 那是结构差异，必须改模板

对方的设计是 **Apple 式三栏**：细图标栏（68px）+ 列表面板（308px）+ 详情面板，一屏看完，
不跳路由。而 Bitwarden 是**左侧导航 + 路由跳页**（`#/vault` 与 `#/vault/item/:id` 是两个页面）。

这一类差异只能靠**改 Angular 模板/组件**解决 ⇒ 属于下面路线 B。

## 2. ② 能不能在源码层改？—— 能，我们现在就在源码层

现状：前端是 **`shiranzby/vw_web_builds @ shypwd`**（Bitwarden Angular monorepo 的源码 fork），
21 批定制**全部写在源码里**，由 CI 的 **29 组产物断言**兜底。

所以"改成这种样式"的两种落地形态：

| 形态 | 做法 | 是否改源码 | 适合 |
|---|---|---|---|
| **换皮** | 新增一个 CSS 段：Apple token → 覆盖 `--color-*` + 组件覆盖 | ✅ 只改 CSS | 现在就能做，风险最低 |
| **换布局** | 改具体页面的 Angular 模板（结构重排） | ✅ 改模板 + CSS | 想要三栏、想要设计稿的页内结构 |

⚠️ 注意：**运行时注入那条路（L4）已经被我们退役过**，不要再走回去 ——
它依赖上游 DOM 不变、无法被构建期断言保护，`/custom.js` 现在还固定 404 就是这个决定的痕迹。

## 3. ③ 自己做一份前端？—— 技术可行，但**我不建议从零写**

### 3.1 真正的成本不在 UI，在**加密与同步**

写一个 Bitwarden 兼容前端，必须自己实现：

| 模块 | 具体内容 | 风险 |
|---|---|---|
| 密钥派生 | 主密码 →（PBKDF2 / Argon2id + 服务端返回的 iterations/salt）→ 主密钥 → 拉伸密钥 → 用户密钥 | 实现错 → **既有数据解不开** |
| 数据加解密 | 条目的 EncString（AES-CBC/CTR + HMAC）、`encType` 多种变体、字段级加解密 | 同上 |
| 组织密钥 | 用户公钥/私钥（RSA-OAEP）、组织密钥的包装与解包、共享条目 | 实现错 → 组织数据不可读 |
| Send | 独立的密钥派生与访问流程（含密码保护的 Send） | 分享出去的链接失效 |
| TOTP / 附件 / 推送 | TOTP 生成、附件加解密与上传、WebSocket 同步、设备注册与刷新令牌 | 功能缺失 |
| API 客户端 | `/api` + `/identity` 60+ 端点、错误码、限流、状态机 | 长尾工作量 |

这些是 Bitwarden 十多年积累的**核心资产**。重写它们 = 把项目里**最危险、最不能出错**的部分重做一遍，
而收益只是"UI 我说了算"。**一个加密 bug 的代价是用户数据永久损坏**，不是"页面不好看"。

### 3.2 而且"自研前端"≠"摆脱上游"

你仍然要跟 **Bitwarden 的协议与加密格式**（服务端要兼容官方客户端 —— 这是本项目的核心卖点）。
上游改 encType、改 KDF 默认值、改 Send 流程，你照样要跟。**只是从"跟 UI 代码"换成"跟协议规范"，并不会更省事。**

### 3.3 唯一值得考虑的"中间形态"

如果目标确实是**不再跟上游 UI**，性价比最高的不是"从零写"，而是：

> **保留 Bitwarden 的逻辑层（`libs/common`：crypto / API / state），替换 UI 层。**

即：继续用它的加密、API、状态机（GPL-3.0 复用），但页面模板与组件换成设计稿那一套。
这样既拿到 UI 自主权，又不用重造加密。

## 4. 三条路线对比

| | **A. 换皮**（推荐先做） | **B. 换 UI 层** | **C. 从零自研前端** |
|---|---|---|---|
| 做什么 | Apple token + 组件外观覆盖进 `vaultwarden.css` | 在 Angular 里重写目标页面模板，逻辑层继续复用 | 全新 SPA + 自己实现加密/API |
| 能拿到 | 配色/字体/圆角/密度/深色，**约 60~70% 观感** | A 的全部 **+** 三栏布局、页内结构 | 100% 自由 |
| 拿不到 | 三栏布局、页内结构 | 彻底脱离 Angular/上游（仍受 GPL-3.0） | （但代价见 3.1） |
| 工作量 | **小**（1~2 个批次，与现有 21 批同量级） | **中~大**（每页一个模板重写；重点 5~6 页） | **很大**（数月级 + 安全审计） |
| 风险 | 低（纯 CSS，29 组断言可兜） | 中（改模板后上游 rebase 冲突面变大） | **高**（加密正确性 / 数据损坏） |
| 移动端 | **完全不受影响**（只加覆盖层） | 需逐页回归（我们最大的投入在移动端） | 要**另做一套移动端设计**（现有设计稿只有 1440×900） |
| 后续维护 | 照旧跟上游（每批半天内） | rebase 成本上升，需要自建断言 | 自己维护一切（含安全修复） |

## 5. 我的建议（分三步走）

**第一步：把设计系统的"皮肤"移植进来（路线 A）。**
- 在 `vaultwarden.css` 新增一个段（比如 `Z 段`）：Apple token → `--color-*` 覆盖 + 字体栈 +
  圆角/阴影/聚焦环 + 按钮/输入框/卡片/表格/TOTP 徽章外观。
- desktop/移动**共用**同一套 token（移动端现在的适配不会被动到，因为它改的是选择器与尺寸，不是配色）。
- 交付物：新版本 + 一组新断言 + 前后对比截图，你再决定要不要继续。

**第二步：只重做"结构确实不同"的页面（路线 B 的子集）。**
- 从你的痛点排序：**设置页（我的账户 / 安全 / 外观 / 域名规则）→ 条目详情 → Send 表单 → 密码库列表**。
- 这几个页面在 Angular 里换模板，逻辑层（表单、加密、API）全部复用 —— 这是"自己掌控 UI"的性价比最高点。
- ⚠️ 这一步会让上游 rebase 的冲突面明显变大，需要配套调整我们的断言策略。

**第三步：只有在"确认要彻底脱离上游"时才讨论。**
- 若真要做，做法是**把 `libs/common` 抽成依赖、只维护自己的 UI 层**，而不是从零实现加密。

---

## 6. 需要你拍板的四件事

1. **先做第一步（换皮）吗？** —— 低风险，能立刻看到 60~70% 的观感变化。
2. **设计稿里哪些*结构*你确实想要？** 特别是：要不要那个 **三栏（图标栏+列表+详情）**？
   它决定第二步的规模 —— 三栏是最大的结构改动，因为它把"列表页 + 详情页"合并成一屏。
3. **是否接受"以后不再跟上游前端"？** 接受的话我按"分阶段脱离"规划；不接受就守住路线 A。
4. **移动端怎么办？** 现有设计稿**只有桌面 1440×900**。我们最大的投入在移动端 ——
   如果走路线 B/C，需要**另做一套移动端设计**（或者由我按同一套 token 推导）。

## 7. 客观限制与风险提示

- **许可证**：前端产物来自 Bitwarden clients，是 **GPL-3.0**；复用其 `libs/common` 仍受 GPL-3.0 约束。
  只有"完全不含 Bitwarden 代码的新前端"才能自选许可证，但那意味着自己实现加密（见 3.1）。
- **商标**：不能叫 "Bitwarden"，只能表述为"协议兼容"。设计稿里也没有用它的商标。
- **设计稿未覆盖的部分**：通行密钥/SSO/组织管理/附件详情/导入的完整字段映射/移动端。
  若要落地，这些页面需要**按同一套 token 补设计**。
- **换皮不是零风险**：`--color-*` 覆盖会牵动 282 个变量之间的关系，
  深浅两套 + 三种密度都要逐屏回归（我们有现成的探针，可自动化）。
- **别把"设计稿好看"直接等同于"改成它更好用"**：设计稿是**静态示例数据**，
  没有覆盖空态/长列表/超长文本/错误态/加载态这些真实场景。落地时必须逐条补。

### 8.0 → 8.1 这两周，上游改了什么

全仓 152 个提交；**动过 `apps/web` 的 38 个、`libs/` 的 59 个**（按路径统计的提交数）。
类型分布：

| 类型 | 典型提交 | 影响 |
|---|---|---|
| **VFO1（密码库前端大改版）** | `Restructure the Password Manager side navigation (web)`、`Introduce vault items table component`、`VFO1 Side nav vault scoping`、`add the My folders page`、`Introduce Web's VaultNextComponent for VFO1` | **改的正是我们定制最深的三处**（侧边导航 / 列表 / 页面结构） |
| 加密包重构 | `refactor(crypto): move {auth,billing,vault,tools,platform,key-management} callers to @bitwarden/legacy-crypto`、`Move LockService into libs/unlock` | 目前是**重构不是修 bug**，但触及加密代码 ⇒ 需要盯 |
| 术语 / 文案 / 翻译 | `Policies list & drawers terminology updates`、`Autosync the updated translations`、`Update tooltip wording` | 无实质影响 |
| 真 bug 修复 | `Login Buttons Overlap Owner and Name Elements When Resizing Browser` | 少量 |
| 版本号 / 依赖 | `Bumped client version(s)` | 无影响 |

### 所以"要不要跟上游前端"—— 分两层，答案不同

- **UI 层：可以不必跟。** 上游正在做的 VFO1 是**桌面导向**的 IA 重做，而它动的
  侧边导航 / vault 列表 / Send 恰好是我们定制最深的三个地方 —— 跟着 rebase 的冲突面很大，
  对"移动端好用"这个目标却几乎没有收益。
- 🔴 **但有一条红线：加密与协议层必须跟。** `libs/common`（现拆为 `@bitwarden/legacy-crypto`）里的
  KDF、encType、密钥包装一旦有实质修复，必须跟进，否则会出现
  "官方客户端能解、我们解不开"。**纯 UI 改动可以跳过。**

⇒ 建议的维护姿态：**冻结 UI，但保留随时能跟的能力** —— 
跟进时只筛 `libs/common`(crypto) / 协议载荷 / 安全相关；UI 改动直接跳过。
这样既省掉大部分 rebase 成本，又不丢安全性。

### 顺带核实："卡片不统一"确实存在，且可量化

设计系统里被当作"卡片/面板"的类，实际参数是 **3 套内边距 × 3 种圆角**：

| 类 | padding | radius | 背景 |
|---|---|---|---|
| `.card` | `var(--space-5)` = 20px | `--radius-lg` = 18px | 白 |
| `.report-card` | 18px | 18px | 白 |
| `.opt-card` | 12px 14px | `--radius-md` = 12px | 白 |
| `.dropzone` | 26px 18px | 12px | `--surface-warm` |
| `.stat` | 14px 16px | **无圆角** | `--surface-warm` |
| `.notes` | 14px 16px | **无圆角** | `--surface` |
| `.gen-out` | 12px | **无圆角** | `--surface` |
| `.banner` | 6px 8px 6px 10px | **无圆角** | `--accent-soft` |

⇒ 这是**真实问题**，不是错觉。可以给出一份"统一为一套卡片规范"的补丁
（例如：统一 18px 内边距 + `--radius-lg` + `--bg`，次级面板用 `--surface` + `--radius-md`），
作为采纳这套设计系统的第一步。

## 附二：结构实验勘察（密码库页 → 设计稿结构）

实验分支：`design-structure-proto`（在 fork 里，**不影响 `shypwd` 与线上**）。

### 设计稿的目标结构（从 `pages/02-vault.html` 提取）

```
.app
 ├ header .appbar     顶栏：品牌 + 全局搜索(Ctrl K) + 锁定 / 注销 / 头像
 └ .shell
    ├ nav .rail       68px 图标栏：密码库 · 验证码 · Send · 工具 · 报告 ·（分隔）· 设置
    └ .views
       └ section.view
          ├ aside .filters #vault-filters   筛选列
          ├ .list-body / .cols-vault        列表

```

### 我们现在的结构（`vault.component.html`，126 行）

```
<app-vault-header>                         页头：搜索 + 新增 + 筛选
<div class="tw-flex">
  <div class="tw-basis-1/4"> <app-vault-filter>   ← 左筛选 25%
  <div class="tw-basis-3/4"> <app-vault-items>    ← 右列表 75%
```

**差异的本质**：不是"样式不同"，而是
① 左侧完整导航 → 68px 图标栏；
② 列表与详情**同屏**（我们从"列表页 + 详情页"两个路由，变成一屏两块）。
